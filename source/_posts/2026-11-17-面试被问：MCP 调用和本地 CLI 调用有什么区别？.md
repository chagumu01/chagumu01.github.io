最近如果面的是 AI Agent、大模型应用开发相关岗位，MCP 基本已经绕不开了。

但面试官如果问：

**“MCP 调用和直接调用本地 CLI 有什么区别？”**

其实他大概率不是想听你背一遍 MCP 的定义。

因为你如果只回答：

“MCP 是 Model Context Protocol，是一种标准协议；CLI 是 Command Line Interface，是命令行接口……”

不能说错，但基本也就停留在“知道这两个名词”的程度。

这道题真正有意思的地方是：

**既然 Agent 已经可以执行 Shell，很多事情直接调 CLI 就能做，为什么还要 MCP？**

比如操作 GitHub。

直接 CLI：

```
gh pr view 123
```

能不能拿到 PR 信息？

当然能。

操作 Git：

```
git log
git diff
git status
```

也完全没问题。

甚至查数据库，都可以：

```
psql ...
```

那问题就来了。

既然 CLI 什么都能干，我费劲接一个 MCP Server 干什么？

这个问题想明白了，MCP 和 CLI 的区别基本也就想明白了。

## CLI 更像是把“电脑”交给 Agent

我们先看 CLI。

假设我要让一个 Coding Agent 帮我排查项目为什么构建失败。

它可能先执行：

```
npm run build
```

发现报错以后看 `package.json`，然后继续：

```
npm list
```

或者：

```
git diff
```

发现是依赖问题，又继续执行其他命令。

注意这里一个很重要的特点：

**我们事先其实不知道 Agent 下一步会干什么。**

它可能执行 Git，可能执行 npm，可能跑 Python，也可能 grep 一下日志。

这正是 CLI 特别适合 Agent 的地方。

你给它一个 Shell，它就拥有了非常大的探索空间。

今天需要：

```
git log
```

明天需要：

```
git blame
```

后天突然需要：

```
git bisect
```

都不用提前开发新的 Tool。

现成 CLI 有什么能力，Agent 基本就可以直接使用什么能力。

所以如果让我用一句话概括 CLI：

**CLI 给 Agent 的是比较通用的“操作能力”。**

但自由度高这件事，既是优点，也是问题。

比如你只是想让 Agent 查一下订单，却直接给了它一个权限很大的 Shell，那么 Agent 实际获得的能力可能远远超过“查订单”。

而且 CLI 的输出，很多时候本来就是写给人看的。

例如：

```
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
```

人一眼就能看懂。

但从 Agent 系统设计的角度，它并不是特别严格的结构化数据。

这时候 MCP 的思路就开始不一样了。

## MCP 更像是：我把“你能干什么”提前定义好

假设现在不是让 Agent 修代码，而是让它操作公司的订单系统。

我可能给它几个 Tool：

```
get_order
list_orders
get_customer
create_ticket
```

每个 Tool 都明确告诉模型：

你需要传什么参数。

比如：

```
get_order

order_id: string
```

返回结果也可以是结构化的：

```
{
  "order_id": "1024",
  "status": "paid",
  "amount": 299
}
```

这时候 Agent 不需要知道订单系统背后到底是什么。

底层可能调用 HTTP API，也可能调 SDK，甚至 MCP Server 内部最后还是执行了一个 CLI。

Agent 不关心。

它只知道：

**“我现在有一个 get_order 的能力，传 order_id 就能拿订单。”**

这其实是 MCP 和直接 CLI 非常核心的区别。

CLI 更像：

> 给你终端，你自己想办法。

MCP 更像：

> 我把你能使用的能力整理成工具，并告诉你每个工具应该怎么调用。

所以 MCP 真正解决的问题，并不是“怎么执行命令”。

如果只是执行命令，Shell 早就存在几十年了。

它更重要的价值在于：

**怎么把外部系统的能力，以一种比较标准、结构化的方式提供给 Agent。**

## 为什么“结构化”这么重要？

举个简单的例子。

CLI 可能是：

```
company-cli order get --id 1024
```

Agent 首先得知道 `company-cli` 存在。

然后知道 `order get` 怎么用。

还要知道参数叫 `--id`。

执行以后，再从 stdout 里面理解返回结果。

但如果包装成 Tool：

```
get_order(
    order_id="1024"
)
```

模型面对的东西就简单很多。

Tool 的名字告诉它“这个东西干什么”，Schema 告诉它“应该传什么”。

所以从 Agent 的角度看，MCP 提供的不是一个“更高级的 Shell”。

而是：

**一个更明确的能力描述。**

这个区别面试的时候说出来，比背一句“MCP 是标准化协议”要有用得多。

## 还有一个很重要的区别：权限边界

假设公司的订单系统里有这些能力：

```
查询订单
创建订单
修改订单
退款
删除订单
```

但我现在做的是一个客服 Agent。

它只需要：

```
查询订单
查询物流
创建售后工单
```

那我完全可以只暴露对应的 Tool。

Agent 看见的是：

```
get_order
get_logistics
create_ticket
```

至于退款、删除订单这些能力，根本不给它。

这时候系统的能力边界是比较清楚的。

当然，这里不能简单理解成：

**“MCP 安全，CLI 不安全。”**

CLI 一样可以通过容器、系统用户、文件权限、sudo policy、沙箱等方式限制。

真正的区别在于：

**MCP 天然比较适合按照 Tool 去定义能力边界，而 CLI 更多是在操作系统和执行环境这一层控制权限。**

这个表述会准确很多。

## 那是不是 MCP 一定比 CLI 好？

不是。

我反而觉得这是这道面试题最应该讲清楚的一点。

如果已经有：

```
git
docker
kubectl
npm
ffmpeg
python
```

这些非常成熟的 CLI，很多情况下直接让 Agent 使用就很好。

比如我要：

“帮我看看最近是谁改了这段代码。”

Agent：

```
git blame ...
```

结束。

如果为了这个功能专门设计：

```
get_code_last_modifier()
```

然后开发 MCP Server、定义 Schema、处理调用……

多少有点把简单问题复杂化了。

更麻烦的是，今天你封装 `git blame`，明天 Agent 又需要 `git bisect`，后天需要 `git worktree`。

难道每一个都封装成 Tool？

最后很可能变成：

**你为了让 Agent 使用 Git，又重新实现了一套 Git。**

这就是 CLI 最大的优势：

**长尾能力特别强。**

Agent 可以自由组合已有命令，而不是只能调用你提前设计好的几个 Tool。

## 所以实际项目里，我更倾向于两者一起用

如果画一下，大概是这样：

```
                   AI Agent
                      │
            ┌─────────┴─────────┐
            │                   │
           MCP                 CLI
            │                   │
      结构化业务能力        通用操作能力
            │                   │
     CRM / 工单系统         Git / Docker
     订单 / 数据库          npm / Python
     SaaS / 内部服务        grep / ffmpeg
```

当然，这个划分不是绝对的。

GitHub 可以通过 MCP 调，也可以：

```
gh pr view
```

数据库可以做 MCP Tool，也可以直接 `psql`。

真正应该考虑的是：

**我希望 Agent 获得的是一个明确、稳定的业务能力，还是一个自由探索和操作环境的能力？**

前者，MCP 往往比较合适。

后者，CLI 往往更舒服。

而且还有一个挺有意思的情况：

**MCP 和 CLI 甚至可以套在一起。**

比如：

```
Agent
  ↓
MCP Client
  ↓
MCP Server
  ↓
gh CLI
  ↓
GitHub
```

MCP Server 底层完全可以继续调用 CLI。

这时候有人可能又会问：

“最后不还是 CLI 吗？那 MCP 这一层有什么意义？”

其实意义就在于：

**对于 Agent 来说，底层实现被抽象掉了。**

今天 MCP Server 底层用 `gh CLI`。

明天改成 GitHub API。

只要：

```
get_pull_request
```

这个 Tool 对外的契约没有变化，上层 Agent 的使用方式就不一定需要跟着改。

所以两者从来就不是什么非此即彼的竞争关系。

## 如果面试官真问到这题，怎么答？

不要上来背：

“MCP 是 Model Context Protocol，CLI 是 Command Line Interface……”

可以先说你的判断：

> **“我觉得两者最大的区别不是能不能完成任务，而是给 Agent 暴露能力的方式不同。CLI 更像给 Agent 一个通用操作环境，灵活、长尾能力强；MCP 更像把外部能力包装成结构化 Tool，能力边界和输入输出更明确。”**

然后再往下展开：

CLI 的优势是灵活、现成工具多、探索能力强，但需要 Agent 理解命令和输出，权限边界也需要额外设计。

MCP 的优势是标准化、结构化、Tool Schema 明确，也更适合业务系统和受控能力，但代价是多了一层 Server 和 Tool 设计、维护成本。

最后一定别忘了补一句：

> **“实际 Agent 系统里我不会把 MCP 和 CLI 当成二选一，而是根据能力类型组合使用。”**

如果能回答到这里，这道题基本就已经从：

**“我知道 MCP 是什么”**

变成了：

**“我知道为什么需要 MCP，也知道什么时候其实没必要用 MCP。”**

而后者，通常才是技术面试真正想聊的东西。
