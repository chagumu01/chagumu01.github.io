我们可能都经历过这样的时刻：在 IDEA 里把接口写好了，Postman 返回 200，心里想着这个需求总算做完了。结果第二天前端说字段对不上，测试反馈删除记录后列表还在显示，组长又在 PR 里指出权限校验有遗漏。等这些问题处理完，代码还要经过部署、生产验证，功能才真正交到用户手上。为什么我们明明已经写完代码，却仍然有这么多事要做？这恰恰是理解企业研发工作流的入口。

当我们一个人做项目时，想到新功能就能直接修改代码；几个人一起开发，需求就要经过产品、前端、后端、测试和发布等不同角色。每个人理解的“做完”也可能不同。我们不妨沿着一个具体需求走一遍，看看它怎样从一句话变成真正上线的功能，以及每个阶段为什么值得花时间。

## 一、从一个需求看完整研发流程

假设我们正在开发一个心理支持 AI 助手，产品经理在群里提出：用户希望下次打开应用时，还能找到上次聊过的内容。乍一看，后端加个查询接口，前端做个列表不就行了？但我们继续追问：历史记录要保存多久、用户可以删除吗、两个设备能否同步、别人能否通过猜测会话 ID 看到私密内容？同一句需求，在不同角色眼里会拆成不同的问题。

这个需求可以沿着下面的链路推进：

需求提出与评审 → 技术设计与排期 → 任务拆分 → 前后端并行开发 → 自测与联调 → QA 测试 → 代码审核与合并 → 部署上线 → 线上验证与持续监控。

我们先把这条链路当作一张协作地图。实际项目里的步骤会交叠：PR 可以在开发早期就建立，Review 可能早于完整 QA 测试；也有团队先合并到集成分支，再让产品验收。顺序并非唯一，关键是每个阶段都有人负责、有明确产物、有通过标准。

![企业研发团队标准开发工作流-1](/assets/development-workflow/1.png)

| 阶段     | 主要产物                 | 要回答的问题               |
| -------- | ------------------------ | -------------------------- |
| 需求评审 | PRD、验收标准            | 为什么做，具体做到什么程度 |
| 技术设计 | 设计文档、接口契约       | 如何实现，风险在哪里       |
| 任务排期 | Issue、负责人、计划      | 谁来做，如何并行           |
| 开发联调 | 代码、接口、测试结果     | 各模块能否正确协作         |
| 测试审核 | 缺陷记录、Review 结论    | 能否安全合并和发布         |
| 上线验证 | 发布记录、监控、验收结果 | 真实环境是否正常           |

## 二、需求评审决定后续返工有多大

需求阶段最重要的产物是可验证的业务规则。比如产品提出增加对话历史功能，研发不能只理解为新增一张数据表和两个接口。还需要确认历史记录是否跨设备同步，删除属于软删除还是物理删除，是否允许搜索，访客能否访问，以及用户只能查看自己的记录。

这些问题看起来属于细节，实际上可能改变数据库结构、鉴权设计和接口数量。评审时通常由产品经理负责用户场景与规则，研发负责技术可行性和工作量，测试提前提出容易遗漏的边界条件，负责人确定优先级及交付范围。

我们可以把模糊需求改写成可执行的验收条件。比如“能看历史记录”就细化成：登录后按时间倒序显示自己的会话，每页 20 条；手动输入其他用户的会话 ID 时不能读取内容；删除后列表立即隐藏该记录。如果没有这一层确认，后端可能认为删除只要数据库标记成功即可，前端却以为必须彻底清除数据，测试又按第三种理解写用例。等到联调才发现分歧，返工就很难避免。

## 三、技术设计是在编码前控制复杂度

需求明确以后，后端通常需要输出一份与任务规模匹配的技术方案。对于简单接口，几段设计说明可能已经足够；涉及数据迁移、并发一致性或跨系统改造时，就需要更完整的方案和评审。

我们先别急着写 Controller。以对话历史为例，如果数据库已经有 `conversation` 和 `message` 两张表，我们需要先弄清会话 ID 如何关联消息、用户 ID 如何参与权限过滤，是否有索引支持时间倒序分页。接下来才是接口：前端传入页码和每页数量，后端返回列表及总数；查不到记录时返回空数组，越权访问则按约定返回错误。把这些写成技术方案，前端就能用 Mock 数据提前做界面，后端也能按同一份契约实现。对于跨模块修改，还要提前评估数据迁移、缓存失效、旧版本兼容和回滚策略。

接口契约通常需要统一请求路径、方法、字段含义、成功响应、错误码和鉴权方式。例如：

```
GET /api/conversations?page=1&pageSize=20
Authorization: Bearer <token>
{
  "code": 0,
  "data": {
    "items": [
      { "id": "c101", "title": "一次历史对话" }
    ],
    "total": 1
  }
}
```

以上仅是便于理解的示例格式，正式项目应遵循现有 API 规范。设计完成后，还应判断是否需要数据库变更脚本、兼容旧客户端、灰度开关和回滚方案。项目越复杂，提前思考这些问题的收益越明显。

## 四、把设计拆成可以独立追踪的任务

技术方案通常无法直接变成多人协作计划，还需要拆出有明确边界的任务。比如历史记录功能可以分为数据结构与迁移、后端列表及详情接口、前端列表页面、权限与删除能力，以及联调和测试用例。

在 GitHub、GitLab 或 Linear 中，可以用 Issue 管理任务。一个合格的 Issue 至少包含背景、目标、工作范围、验收标准、负责人以及依赖关系。任务状态可按团队需要设置为待办、进行中、待审核、待验证和已完成。

我们可以想象三个人同时做这个需求：A 负责后端接口和权限，B 负责前端列表与详情页，C 负责测试场景与验收。三个人共用一份接口契约，却在各自 Issue 中记录自己的验收标准。这样 A 的接口还没写完时，B 可以先用 Mock 开发，C 也可以先设计“越权访问”“删除后刷新”“空列表”等用例。Issue 没必要细到每个方法，也不能大到无法判断进度；我们只要确保它能独立交付、独立验证，并且依赖明确。

## 五、前后端并行开发如何避免互相等待

前后端并行的前提是接口约定稳定。在后端编写 Controller、Service、DAO 或 Repository 时，前端可以根据设计稿实现组件和页面状态，并通过 Mock 数据进行开发。等接口部署到测试环境，再切换到真实请求进行联调。

当我们开始联调时，常见问题往往非常具体。比如前端约定从第 1 页开始请求，后端分页实现却按第 0 页处理，页面就会少一页；后端已经完成删除，前端却没有清除本地缓存，用户仍能看到被删记录。再比如接口返回 `null`，前端却直接对它调用 `.map()`，页面就报错。联调时我们最好把正常数据、空列表、权限失败、网络超时以及重复请求都过一遍，避免只用一条成功数据证明功能可用。

对于 Java 后端，开发阶段除实现业务逻辑外，还应完成参数校验、统一异常处理、日志记录以及关键单元测试。涉及 MySQL 或 Redis 时，需要检查事务边界、缓存一致性及资源消耗。接口能返回 200，并不能说明整个业务逻辑已经达到交付标准。

## 六、从功能完成到代码合并

多人协作通常会使用功能分支隔离开发。以 GitHub 的常见方式为例，开发者先同步最新主干，再创建功能分支，分批提交逻辑清晰的 Commit，完成自测后推送远程并建立 Pull Request。

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/conversation-history

# 开发、测试并提交
git add .
git commit -m "feat: add conversation history API"
git push -u origin feat/conversation-history
```

在 PR 描述里，应说明本次改动解决什么问题、如何测试、是否有数据库变更，以及是否存在兼容性影响。最好关联对应 Issue，让需求、代码和验证记录能够互相追溯。主干在开发期间可能变化，因此合并前还需要根据仓库策略同步主干并处理冲突。

Code Review 的关注点也超出代码风格。审核者需要检查业务规则是否正确、模块职责是否清晰、异常处理是否完整、权限校验是否缺失，以及修改是否可能影响其他功能。CI 则适合自动运行编译、测试、静态检查等重复工作。人工审核与自动化检查互相补充。

我们尤其需要分清几个状态。比如 PR 已经通过 Review，只表示代码改动满足当前审核要求；合并到 `main`，表示改动进入了目标分支；测试通过，表示指定范围内的验证结果合格；产品验收通过，表示业务预期得到确认；生产发布成功，才代表新版本真正部署到用户环境。它们的顺序会随团队分支策略变化，但每一项都应单独记录，否则很容易出现“明明合并了，怎么用户还看不到功能”的沟通问题。

## 七、测试为什么要分层进行

测试是逐步缩小风险的过程。开发自测先验证核心逻辑和典型异常，联调确保跨模块行为一致，QA 再从需求和真实使用场景出发设计测试。对于影响较大的修改，还可能补充集成测试、性能测试、安全测试和回归测试。

一条有效的 Bug 记录应让其他人能够复现问题：写明环境、操作步骤、预期结果、实际结果、相关日志或截图以及影响范围。开发修复后，需要由测试复验，并根据影响面执行相关回归。修复一个分页问题时，除了确认当前页面正常，还应验证边界页、空列表和权限场景。

我们再看一个更隐蔽的例子：测试人员先用 A 账号创建一段对话历史，再用 B 账号直接请求 A 的会话详情。如果后端只按会话 ID 查询，没有限制当前登录用户的 ID，就可能造成隐私数据泄露。普通功能自测很容易遗漏这种情况，因此关键场景需要从验收标准反推用例。越早发现问题，修复成本通常越低，这也是我们要提前联调、持续集成、小批量提交的原因。

## 八、代码上线以后工作仍然没有结束

测试环境通过，只说明在特定配置和数据条件下达到了预期。生产环境有不同的流量、数据规模、缓存状态和权限配置，上线必须被当作独立的工程过程。

正式发布前，需要核对版本、配置项、数据库迁移、依赖服务和回滚条件。发布可以由运维执行，也可以通过自动化流水线完成；前后端的部署顺序由接口兼容策略决定。对高风险功能，还可以先灰度到少量流量，观察错误率、延迟和业务指标，再逐步扩大范围。

上线后的第一件事是验证关键链路，例如登录、查看历史记录、打开详情及删除记录。与此同时，要关注服务日志、告警和指标变化。出现严重异常时，应根据预先制定的预案回滚版本或关闭功能开关。上线验收完成以后，Issue 和版本记录才能形成可靠的交付闭环。

## 九、AI Coding 应该放在流程的什么位置

AI Coding 可以提高实现速度，也会让一些原本靠开发者自行把关的问题更加突出。模型能够生成接口、数据库迁移、测试用例乃至 PR 描述，但它不一定完整理解业务边界、仓库规范和线上约束。

比较稳妥的协作方式是把 AI 当作受约束的实现参与者。需求阶段让它辅助找遗漏的验收条件，设计阶段用它比较方案与风险，编码阶段要求只修改指定模块，测试阶段让它根据验收条件补充用例，Review 阶段再由 AI 和人工共同检查变更。

如果我们让 Agent 帮忙实现对话历史功能，可以先提供需求和验收条件，让它阅读仓库并列出将要修改的文件，再让它生成接口与测试，最后通过 CI 和人工 Review 验证结果。每一步都留下可检查的产物：需求对应 Issue，设计对应技术文档，代码对应 Commit 或 PR，验证对应测试日志。这样就算 Agent 在十几轮操作后出现偏差，我们也能回到具体步骤查找原因。尤其要避免让同一个 Agent 完全自行定义需求、编写代码、设计测试并宣布成功；关键验收条件最好由我们独立确认。

一个特别需要警惕的情况是，AI 自己生成了代码，又根据自己对需求的理解编写测试，最后宣布测试全部通过。测试通过只能证明代码符合当前测试断言，所以验收标准和关键用例应有独立的人工确认，重要变更还要在真实集成环境验证。

## 十、个人项目如何实践企业级工作流

个人开发没有必要照搬大型团队的所有审批动作，但完全可以保留有价值的工程约束。一个轻量工作流可以是：建立 Issue 说明目标与验收标准，写简短设计和接口约定，创建功能分支，小步提交并运行测试，通过 PR 检查差异，部署预览或测试环境，最后发布并做冒烟验证。

当项目规模增加，再逐步引入自动化 CI、分支保护、发布记录、监控告警和任务看板。重要的是根据项目风险选择流程厚度，而不是为了使用工具而增加环节。

回头看完整研发链路，会发现每个环节都在留下可供下一位协作者使用的证据：PRD 证明需求已明确，技术设计说明改动方案，Issue 记录责任和状态，测试报告证明验证范围，PR 保存审核过程，发布记录连接代码与线上版本。一个成熟的研发过程，最终依靠这些可追踪的交付物，把个人完成的代码转化为团队能够持续维护的产品。
