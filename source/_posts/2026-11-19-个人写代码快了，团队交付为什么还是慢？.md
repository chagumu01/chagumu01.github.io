最近使用 AI Coding 工具时，我越来越明显地感觉到，写代码这件事正在变得简单。

以前我们需要半天实现的接口，现在可能只需要把需求描述清楚，交给 Codex 或 Claude Code，十几分钟就能得到一份能够运行的实现。再配合 Agent，数据库操作、单元测试、代码重构，甚至 Git 提交都可以让 AI 协助完成。

但这也让我产生了一个疑问：**当每个人都能更快地写代码，整个团队的项目交付速度，真的能同比例提升吗？**

假设我们负责一个多人协作项目。后端开发者已经完成接口，前端却还在等待联调；功能测试已经通过，PR 还在排队审核；代码终于合并，却因为部署环境的问题迟迟无法上线。

如果我们把编码时间从两天压缩到半天，这些等待会自动消失吗？

显然不会。

最近看到腾讯开源的 [LoopForge](https://github.com/Tencent/LoopForge)，我觉得它提供了一个很有意思的切入点。它尝试把 Coding Agent 从个人编程环境扩展到团队研发流程，让 Agent、自动化脚本和人工审批共同参与软件交付。

这让我重新思考：当 AI 已经足够擅长写代码，我们接下来究竟应该优化什么？

## 一、个人编码提速为什么没有直接带来团队交付提速

我们先用一个具体需求来理解这个问题。

假设团队正在开发一个 AI 心理支持助手，现在产品经理提出，希望增加对话历史功能，让用户能够查看、搜索以及删除之前的咨询记录。

后端开发者需要设计数据结构和接口，前端需要实现历史记录页面，测试需要验证权限、删除和分页逻辑。

在传统开发方式下，后端可能需要两天完成接口。现在有了 Coding Agent，我们将需求和项目上下文交给 AI，它可能只需要半天就能生成大部分代码。

但需求从提出到上线，还要经过需求评审、技术设计、任务拆分、联调、Review、测试和发布。

假设这些环节原本串行耗时十天，而 AI 将其中两天的编码工作压缩到半天，那么整个需求仍然需要八天半才能上线。

**我们把编码环节提速了 75%，整个交付周期却只缩短了 15%。**

这只是一个简化的示例，但揭示了一个问题：我们很容易把开发者完成代码的速度，当成整个项目的交付速度。

实际交付涉及多个协作环节。即使其中某个环节已经被 AI 大幅加速，其他环节仍然可能成为瓶颈。

更值得注意的是，当 AI 可以快速生成更多代码时，如果测试和 Review 的处理能力没有提高，待审核、待验证的任务反而可能越来越多。

所以，个人提效之后，我们需要继续追问：**这些代码如何被团队接收、验证并最终交付？**

## 二、从 Coding Agent 到团队研发平台，我们缺少什么

我们先看看平时使用 Coding Agent 的开发方式。

以 Codex 为例，我们打开项目，描述需求，Agent 阅读仓库、修改代码、运行测试，最后由我们检查结果并提交。

对于单人开发，这是非常顺畅的一套流程。

但放到团队中，新的问题就出现了。

我们如何确保不同 Agent 理解的是同一份需求？多个任务是否可以同时执行？Agent 修改的代码应该在哪里运行？谁来审核生成的代码？执行失败以后，如何知道是哪一步出了问题？

如果每个开发者都维护自己的 Prompt、工具配置和开发习惯，团队就很难积累统一的交付规范。

这正是 LoopForge 值得研究的地方。

它把 Coding Agent 放进一套更完整的软件交付体系中。编程工作依然由 Codex、Claude Code 等执行器承担，但外层新增了任务组织、角色分工、执行环境、标准流程和人工关口。

我们可以把它理解为三个层次。

| 层次         | 主要负责什么         | 代表能力                             |
| ------------ | -------------------- | ------------------------------------ |
| Coding Agent | 执行具体编码任务     | Codex、Claude Code                   |
| 执行与验证层 | 提供环境、测试和产物 | Docker 沙箱、脚本、测试日志          |
| 交付编排层   | 组织角色、流程和审核 | LoopForge 的 SOP、Main Bot、人工关口 |

从这个角度看，Coding Agent 负责提高单个任务的执行效率，LoopForge 则尝试解决这些任务如何按照团队规则连接起来的问题。

而它最关键的设计之一，就是 SOP。

## 三、SOP 让团队经验变成可以重复执行的流程

SOP 是 Standard Operating Procedure，即标准作业程序。

我们可以把 SOP 理解为一套经过明确约定的执行步骤。每一步由谁负责、需要什么输入、输出什么产物、满足什么条件才能继续，都可以提前定义。

例如，我们已经有一套经过验证的后端开发流程：

1. 分析需求与业务边界。
2. 输出技术方案。
3. 修改代码并编写测试。
4. 独立执行代码审查。
5. 运行构建与自动化测试。
6. 等待人工确认后交付。

如果这些步骤每次都需要我们手动向 Agent 重新说明，既容易遗漏，也增加了重复沟通成本。

LoopForge 的思路是将这样的过程编排为 SOP。它支持 Agent 节点、脚本节点、人工审批节点以及可复用的子流程。

假设我们把心理支持助手的历史记录需求交给这套流程，可能会发生下面的事情。

首先，需求分析 Agent 阅读任务，整理出历史记录查询、用户隔离、删除行为等验收条件；接着，开发 Agent 在独立工作区修改 Java 后端代码；然后，审查 Agent 检查权限、异常处理和项目规范；脚本节点运行 Maven 测试；最后，我们在人工审批节点检查产物，决定继续交付还是退回修改。

如果 Review 发现接口缺少用户身份校验，流程可以退回开发环节，重新完成修改和验证。

这个过程的价值在于，我们可以复用那些已经证明有效的工作方式。

**一次开发中发现的问题，有机会变成下一次开发必须执行的检查。**

例如，团队之前因为缺少权限校验出现过越权访问问题，那么我们就可以把权限检查加入后续 SOP 的验收要求。这样经验就不再只停留在某个人的记忆或某篇复盘文档中。

当然，SOP 也需要根据任务复杂度调整。修复一个文案错误，可能无需经历完整的设计与多轮审查；涉及数据库迁移和权限修改，则需要更严格的质量门禁。

## 四、Agent 可以并行工作，但谁来保证结果能够集成

我们再考虑另一个场景。

假设前端 Agent 正在实现历史记录页面，后端 Agent 正在开发查询接口，测试 Agent 则负责生成测试用例。

三个 Agent 同时工作，看起来非常高效。

但如果后端使用 `conversationId` 作为字段名，前端却按照 `sessionId` 处理，集成阶段就会出现问题。

更复杂的情况是，多个 Agent 同时修改同一份核心代码，导致 Git 冲突、业务逻辑不一致以及测试失败。

因此，多 Agent 协作最重要的前提，是任务之间有清晰的依赖关系和接口契约。

LoopForge 的 SOP 通过节点依赖组织执行顺序，并为任务提供独立沙箱。它能够减少运行环境之间的干扰，让每次执行产生的代码、日志和测试结果保留在对应工作区中。

不过，**环境隔离只能解决执行冲突的一部分，代码层面的集成冲突仍然需要设计约束和验证机制。**

我们可以进一步把协作规则放进 SOP 中，例如要求前后端开始开发前先确认接口文档，要求涉及共享模型的修改经过统一设计，以及要求所有功能在合并之前运行集成测试。

由此可以看出，让多个 Agent 同时编程并不困难，真正重要的是让它们的结果能够可靠集成。

## 五、代码生成以后，谁来承担质量责任

随着 AI 生成代码的比例不断增加，我认为 Code Review 的重要性反而会提高。

过去，我们审核一个 PR，主要面对的是开发者自己编写和理解的代码。现在，一个 Agent 可以一次生成大量文件，甚至跨越多个模块。

如果代码生成速度提高，但审查能力没有跟上，就会形成新的质量瓶颈。

LoopForge 的做法是把质量检查直接放进交付流程。

例如，开发 Agent 完成修改后，可以交给独立审查角色检查，再通过脚本执行构建、Lint 和自动化测试。对于需要业务确认的操作，则在人工关口等待验收。

这里我比较认可的一点，是它将确定性脚本和 Agent 区分开来。

像编译、格式检查、单元测试这类有明确执行规则的任务，使用脚本更直接，也更容易复现。需求理解、方案分析和代码审查这类需要上下文判断的工作，则可以交给 Agent 辅助完成。

人工关口负责那些需要业务判断、风险接受或正式授权的决策。

这样的分工能让我们避免把所有任务都交给大模型处理。

但也要意识到，独立审查 Agent 不一定能够发现全部问题，自动化测试通过也只证明当前测试覆盖的行为满足断言。

所以，在真实项目中，我们仍然需要建立可信的验收标准，并对权限、数据安全和高风险变更设置必要的人工审核。

## 六、让研发流程可观测，才能知道团队究竟慢在哪里

前面我们一直在讨论交付瓶颈，但还有一个实际问题：团队如何知道瓶颈在哪里？

如果我们只看开发者每天提交了多少代码，很难判断需求究竟为什么交付缓慢。

我们更需要观察的是，一个需求进入系统以后，在哪个阶段停留了多久、经历了多少次失败、产生了多少次返工。

LoopForge 提供节点执行状态、日志、产物、审批记录和研发效能统计。结合这些数据，我们就有机会分析整个工作流的运行状况。

例如，假设某条 SOP 连续执行了二十次，我们发现：

- 开发实现平均需要 15 分钟。
- 自动化测试平均需要 5 分钟。
- 人工审核平均等待 6 小时。
- 每三个任务中就有一个需要退回修改。

这些数字是假设性的，但能够帮助我们理解一个关键问题。

如果开发环节已经很快，那么继续更换更强的模型，可能只能带来有限收益。相比之下，优化审核机制、减少返工和改进需求质量，可能更有价值。

LoopForge 官方还介绍了基于运行轨迹分析 SOP 健康度和生成改进建议的方向。它使我们能够进一步思考：能不能让 Agent 不断复盘自己的交付流程，识别高频失败原因，并提出流程改进方案？

不过，流程改进建议仍然需要验证。修改 Prompt 或 SOP 以后，应通过历史任务、固定测试集和实际运行指标确认是否真的有效。

否则，我们可能只是把旧问题替换成新的问题。

## 七、从个人 AI Coding 到团队 AI 交付，还有多远

LoopForge 提供了一种值得关注的工程思路，但它也无法自动解决所有研发管理问题。

首先，需求本身可能仍然存在歧义。如果团队没有统一的业务目标，Agent 很难替大家做出正确的产品决策。

其次，SOP 需要维护。项目架构、技术规范和业务规则发生变化时，原来的流程可能需要同步调整。

再次，多 Agent 协作也存在成本。我们需要考虑 Token 消耗、沙箱资源、任务依赖、审查质量和失败重试。

对于只有几个人的小项目，过于复杂的流程可能让原本简单的修改变得繁琐。对于多人长期协作、交付规范明确且重复任务较多的项目，这类平台才更容易体现价值。

因此，我认为应该根据项目的实际瓶颈选择工具。

如果我们只是想更快实现一个功能，Codex 或 Claude Code 已经能够提供很大帮助。

如果我们需要多次重复执行同一类开发任务，可以考虑将成功经验整理成 Skill、脚本或者 SOP。

如果我们需要协调多个 Agent、管理执行环境、追踪任务状态并建立审批机制，那么 LoopForge 这样的交付编排平台就更值得研究。

## 八、我们下一步需要优化的是整个交付系统

回到最初的问题：个人写代码快了，团队交付为什么还是慢？

现在我们可以从两个层次理解。

第一个层次是个人生产力。Coding Agent 大幅降低了代码实现的成本，让开发者可以把更多精力投入到需求理解、架构设计和问题验证中。

第二个层次是团队交付能力。代码需要经过协作、集成、审核、测试和发布，才能真正转化为业务价值。

LoopForge 的探索，恰好把我们带到了第二个层次。

它让我们看到，AI 在研发中的应用可以进一步扩展到角色协调、工作流执行、质量检查和流程优化。

对我来说，这也引出了一个更值得继续研究的方向：**如果我们能把团队经过验证的开发经验沉淀为可执行的 SOP，再通过运行数据持续改进这些 SOP，是否能够形成一套不断优化的 AI 研发交付系统？**

在这样的系统中，Agent 不仅参与代码实现，还参与交付流程的执行和复盘；人则负责需求目标、关键决策和质量标准。

真正值得追求的研发效率，也就不再局限于一小时能生成多少代码，而是团队能否以更低的协作成本、更稳定的质量，把功能持续交付给用户。

毕竟，我们最终想要的，是让一个想法更可靠地成为产品。
